# Live Posts — Spec

> Receives a visitor's post over the WebSocket, validates it, builds and stores it on the server, broadcasts it to every client and replays the stored posts to each new connection.

## Intent

A visitor publishes a name and a text and every connected visitor sees it at once; a visitor who connects later still sees what was already published. This is the real activity of the network, held only in server memory.

## Scope

Owns:

- Receiving a publish message, validating it and rejecting it when invalid or over the rate limit.
- Building the stored post on the server, appending it to the in-memory history and broadcasting it to all connected clients.
- Sending the stored posts to each new connection.
- Bounding the history and limiting the publish rate per connection.

Non-goals:

- Chat messages. The global-chat slice owns them; this slice only shares the transport.
- Persistence, accounts, editing and deleting posts.
- The posts read from the fake-data API. The social-feed slice owns them, and the two lists are never merged, so no id policy between the two sources is needed.
- Layout and visual states. Live posts are meant to show in the center panel above the API posts, newest first; that belongs to a future design file.

## Contract

| Item | Value |
|---|---|
| Transport | One WebSocket connection shared with global-chat; each message carries a `type` that tells posts from chat |
| Client publish message | Author name and text, nothing else is read |
| Stored post | Unique id, author name, content, formatted time, all built by the server |
| Validation | Name and text are trimmed, non-empty and within a maximum length (starting values: name 30, text 280) |
| On rejection | An error message goes to the sender only; nothing is stored or broadcast |
| Broadcast | The new post goes to every connected client, the sender included |
| History | Sent to each new connection; holds only the most recent posts (starting value: 100), the oldest is dropped first |
| Rate limit | Per connection, a maximum number of publishes in a time window; value and mechanism open; an over-limit publish is rejected like an invalid one |

## Invariants

1. The id and the time of a stored post are always generated by the server, never taken from the client message. [none]
2. Every stored post has a unique id. [none]
3. If a publish message is unparseable, has a wrong type or a missing field, has a name or text that is empty after trimming, or exceeds a maximum length, then nothing is stored or broadcast and the sender receives an error message. [none]
4. When a valid publish arrives, the server appends the post to the history and broadcasts it to every connected client. [none]
5. When a client connects, the server sends it the stored posts. [none]
6. While the history holds the maximum number of posts, appending a new post drops the oldest one. [none]
7. If a connection exceeds the publish rate limit, then the post is not stored or broadcast and the sender receives an error message. [none]
8. Author name and text are inserted into the page as text, never as markup, including posts that arrive over the WebSocket. [none]
9. Incoming WebSocket messages are parsed with a schema at the boundary, and only the parsed result is used afterwards. [none]
10. If one client sends a malformed message, then the other clients' connections stay open and the broadcast keeps working. [none]

## Deferred / Open questions

- Testing gap: every invariant is tagged `[none]` because no code exists yet. The executor writes the tests at implementation time; WebSocket tests need a harness choice first.
- Maximum lengths (30 and 280) and history size (100) are starting values.
- Rate limit count, window and mechanism. Decided when the slice is implemented.
- Time format: locale and timezone of the "formatted time", and whether the server or the client formats it.
- Id scheme (for example a UUID or a counter). Only uniqueness is contracted.
- Whether a connecting client gets the history strictly before any later broadcast. Invariant 5 only promises delivery; decide at implementation, once the connection handling is known.
- WebSocket endpoint and message envelope, shared with global-chat. Decided when the first of the two slices is implemented, then recorded in the other.
- Whether the sender's error shows inline in the publish form. Decided in the design file.

## Acceptance criteria

1. Given two connected clients, when one publishes a valid name and text, then both receive the post with a server-made id and formatted time. [none]
2. Given a stored post, when a third client connects afterwards, then it receives that post as history. [none]
3. Given a publish message that also carries an id and a time, when it is stored, then the id and time are the server's own. [none]
4. Given an empty text or a text one character over the maximum, when it is published, then the sender gets an error and the other client receives nothing. [none]
5. Given a text containing `<script>`, when it reaches the clients, then both show it as escaped text. [none]
6. Given the history is full, when one more post is published, then the history still holds the maximum and the oldest post is gone. [none]
7. Given one connection over the rate limit, when it publishes again, then it gets an error and the other clients are unaffected. [none]
