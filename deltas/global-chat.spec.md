# Global Chat — Spec

> Receives a visitor's chat message over the WebSocket, validates it, builds and stores it on the server, broadcasts it to every client and replays the recent messages to each new connection.

## Intent

Every connected visitor talks in one shared room in real time, and a visitor who connects later sees the recent conversation. Messages live only in server memory.

## Scope

Owns:

- Receiving a chat message, validating it and rejecting it when invalid or over the rate limit.
- Building the stored message on the server, appending it to the chat history and broadcasting it to all connected clients.
- Sending the chat history to each new connection.
- Bounding the chat history and limiting the chat rate per connection.

Shares the single WebSocket connection with the live-posts slice; each message carries a `type` that tells chat from posts. This slice specifies only chat messages and the chat history. The endpoint and message envelope are decided when the first of the two slices is implemented, then recorded in the other.

Non-goals:

- Live posts. The live-posts slice owns them.
- Private messages, rooms or channels, accounts or sessions.
- Presence: online count, join and leave notices, typing indicator.
- Editing, deleting and persisting messages.
- Layout and visual states: a future design file.

## Contract

| Item | Value |
|---|---|
| Client chat message | Author name and text; the name travels in every message, so the server keeps no per-connection state |
| Stored message | Unique id, author name, text, formatted time, all built by the server |
| Validation | Name and text are trimmed, non-empty and within a maximum length (starting values: name 30, text 200) |
| On rejection | An error message goes to the sender only; nothing is stored or broadcast |
| Broadcast | To every connected client, the sender included |
| History | Sent to each new connection; holds only the most recent messages (starting value: 50), the oldest is dropped first |
| Rate limit | Per connection, a maximum number of chat messages in a time window; separate from the live-posts limit and more permissive; value and mechanism open; an over-limit message is rejected like an invalid one |

## Invariants

1. The id and the time of a stored message are always generated by the server, never taken from the client message. [none]
2. Every stored message has a unique id. [none]
3. If a chat message is unparseable, has a wrong type or a missing field, has a name or text that is empty after trimming, or exceeds a maximum length, then nothing is stored or broadcast and the sender receives an error message. [none]
4. When a valid chat message arrives, the server appends it to the chat history and broadcasts it to every connected client. [none]
5. When a client connects, the server sends it the stored chat messages. [none]
6. While the chat history holds the maximum number of messages, appending a new one drops the oldest. [none]
7. If a connection exceeds the chat rate limit, then the message is not stored or broadcast and the sender receives an error message. [none]
8. Author name and text are inserted into the page as text, never as markup, including messages that arrive over the WebSocket. [none]
9. Incoming chat messages are parsed with a schema at the boundary, and only the parsed result is used afterwards. [none]
10. If one client sends a malformed message, then the other clients' connections stay open and the broadcast keeps working. [none]
11. A chat message is never stored in or broadcast as part of the live posts history, and a post is never stored in the chat history. [none]
12. The chat rate limit never counts live posts publishes, and the live-posts limit never counts chat messages. [none]

## Deferred / Open questions

- Testing gap: every invariant is tagged `[none]` because no code exists yet. The executor writes the tests at implementation time; the WebSocket test harness is chosen together with live-posts.
- Maximum lengths (30 and 200) and history size (50) are starting values.
- Rate limit count, window and mechanism. Decided when the slice is implemented.
- Time format and who formats it. Same question as live-posts; decide it once for both.
- Id scheme. Only uniqueness is contracted.
- WebSocket endpoint and message envelope, shared with live-posts.
- Whether a connecting client gets the history strictly before any later broadcast. Same open question as live-posts.
- Presence features and chat UI details (auto-scroll, highlighting one's own messages, inline errors). Decided in the design file or a later slice.

## Acceptance criteria

1. Given two connected clients, when one sends a valid message, then both receive it with a server-made id and formatted time. [none]
2. Given a stored message, when a client connects afterwards, then it receives that message as history. [none]
3. Given a message that also carries an id and a time, when it is stored, then the id and time are the server's own. [none]
4. Given an empty text or a text one character over the maximum, when it is sent, then the sender gets an error and the other client receives nothing. [none]
5. Given a text containing `<script>`, when it reaches the clients, then both show it as escaped text. [none]
6. Given the history is full, when one more message is sent, then the history still holds the maximum and the oldest message is gone. [none]
7. Given one connection over the chat limit, when it sends again, then it gets an error and the other clients are unaffected. [none]
8. Given a chat message was sent, when the post history is read, then it holds no new item, and the same holds in the other direction. [none]
